1 · Abstract

Opportunity Radar is a full-stack web platform that closes the distance between a student looking for work and a student ready for it. It aggregates live internships, jobs, hackathons and scholarships into one searchable catalogue; scores a résumé against a specific job description using measured evidence rather than keyword counting; runs a real spoken mock interview through a voice AI agent and returns a graded report; and tracks every application through to its outcome. The system is deployed and operational, comprising a Next.js 16 application, a Supabase Postgres backend with row-level security on every table, and two Python AI services running on a dedicated cloud host.

2 · Problem Statement

The preparation gap

A student applying for their first technical role faces a problem that is not a shortage of information but an excess of it, scattered across incompatible tools. Openings live on a dozen portals with no common format. Résumé feedback, where it exists at all, is generic advice untethered from the specific role being applied for. Interview practice requires another person's time. Applications are tracked, if at all, in a spreadsheet that answers no useful question about how the process is going.

The consequence is a preparation gap: students apply widely but not well. They cannot see which of their skills a particular employer actually asked for, which are genuinely evidenced on their own résumé, or what specific work would close the difference. Four distinct needs go unmet:

Fragmented discovery

Relevant openings are spread across many sources with no single, filterable view.

Unmeasured résumés

Students cannot tell how a given résumé reads against a given role until it is rejected.

Inaccessible practice

Spoken interview rehearsal depends on another person being available to conduct it.

No feedback loop

Nothing connects an application's outcome back to what should be improved next.

3 · Proposed Solution

One system, one continuous loop

Opportunity Radar treats these four needs as one workflow rather than four products. A student discovers a role, measures their résumé against it, receives a specific and actionable list of gaps, closes those gaps with recommended certifications and projects, rehearses the interview aloud, and tracks the application to its result — each stage feeding the next.

Three design principles govern the system throughout, and account for most of its engineering:

I

Evidence over keywords

A skill counts when the résumé demonstrates it. The scoring engine weighs a shipped project above a listed keyword, and every requirement carries the exact quoted text that satisfied it.

II

Never present a number the system did not compute

Where a value is unknown, the interface says so. A missing field is omitted rather than filled with a plausible placeholder, so a student can trust what is shown.

III

Defence in depth on every record

Row-level security is enabled on all database tables, and every read and write additionally carries an explicit ownership filter, so a single misconfiguration cannot expose another student's data.

4 · System Architecture

Three tiers, clearly separated

Presentation tier · Vercel

Next.js 16 App Router · React 19 · Tailwind CSS v4 — 31 pages and 53 server route handlers, rendered on the server by default.

Data tier · Supabase (managed Postgres)

Authentication, Postgres, object storage and realtime channels. Row-level security on every table; 65 timestamped SQL migrations hold the schema history.

Intelligence tier · Cloud VM (systemd + Caddy TLS)

Two independent Python services — the AI Search agent and the Voice Interview agent — each behind TLS and gated by a shared internal secret. The browser never calls them directly; only the application server does.

The separation is deliberate. Long-running AI work — a web-search agent that runs for minutes, a live voice session that holds a WebRTC connection — does not belong in a serverless request. Isolating it on a dedicated host lets each tier be scaled, restarted and reasoned about independently, while the internal-secret gate ensures those services answer only to the application server.

9 · Data Model and Security

How student data is protected

Every table in the database has row-level security enabled, and every table holding student data carries per-user ownership policies covering select, insert, update and delete. A query issued on behalf of one student is constrained by the database itself, not by application logic that could be bypassed.

Application code then adds a second, independent layer: every read and write also carries an explicit ownership filter. Either layer alone would be sufficient; requiring both means a future change to one cannot silently expose data. Schema changes are made only through timestamped migration files, giving a complete and reproducible history of the database.

10 · Engineering Quality

Verification and discipline

The project is held to gates that run on every change: an automated test suite, a full TypeScript type-check across the entire codebase, static analysis, and a production build. Business logic is deliberately extracted from user-interface components into pure, independently testable functions — the scoring engine, the application-funnel statistics, the search-filter builders and the redirect validators are all covered this way.

11 · Deployment and Operations

Live and self-maintaining

The application is deployed on Vercel with continuous delivery from version control: a push builds and releases automatically. The two AI services run under systemd on a cloud virtual machine, each behind a Caddy reverse proxy that terminates TLS and renews certificates without intervention.

Eleven scheduled jobs keep the platform current without any manual work. Overnight tasks refresh opportunities from each source; link-health sweeps verify that listings and certification links still resolve and hide those that do not; further jobs generate deadline notifications and retire stale interview sessions. Long-running routes declare explicit execution budgets scaled to the work they perform, so AI operations complete rather than being cut short.

The result is a platform that maintains its own catalogue: opportunities arrive, dead links disappear, and deadlines reach students without anyone tending the system day to day.

14 · Conclusion

Opportunity Radar demonstrates that the separate stages of career preparation — discovery, assessment, skill-building, rehearsal and tracking — work better as one connected system than as five disconnected tools. Every score it shows is derived from evidence it can quote; every record it stores is protected at the database level as well as in code.

The platform is deployed and operational, integrating a modern web application, a secured relational backend, and two independently deployed AI services including real-time voice. It stands as a complete, working answer to the problem it set out to solve.
