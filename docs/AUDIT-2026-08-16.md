## 2. AI Resume Optimizer & ATS Checker — deep dive

### 2.1 What was tested

A complete, realistic test resume was built through the actual Resume Builder UI (not a fixture): full profile with headline/phone/location/website, a two-paragraph summary, two education entries, two work-experience entries with real bullet points, two projects, seven skills at varying proficiency levels, two certifications, and one award. This exercised every section the scoring engine reads.

That resume was then run through:
1. **ATS Checker** (`/resume/ats`) — targeted mode against a real, realistic job description (Frontend Engineer Intern, 25 lines, responsibilities/requirements/preferred sections).
2. **Resume Optimiser** (`/resume/copilot`) — full run: intake → baseline score → tier decision → Resume A generation → gap checklist → confirming all 4 items → Resume B generation → both variants downloaded.

### 2.2 What works, with evidence

**Section coverage is complete.** The Builder → ATS conversion path (`convertResumeDataToParsedResume`) correctly carried every section into the scoring engine — verified by reading the actual evidence-matrix output, which cited specifics from the experience bullets, project descriptions, and skills list, not just section headers.

**Scoring is evidence-based, not keyword matching.** The matched-requirements list quoted the resume's own text directly:

> "The candidate built and shipped 'Opportunity Radar', a production-scale job-aggregation platform, using Next.js, which is built on React. This demonstrates extensive practical experience with React in a complex, real-world application."

This is exactly the calibration the project's own APP-03/APP-04 fixes were built to produce, and it held up on a fresh, independent test case.

**Suggestions are genuinely actionable.** Each gap included a concrete build brief and named sibling technologies from the same job description — e.g. for a missing Git requirement: *"Build one small, finished project that genuinely uses Git... Pair it with React, TypeScript, CSS if you can — those are the other technologies this job description calls out. Push it to GitHub with a short README... then list it under Projects."*

**The fabrication guard is real, not just documented.** Confirming the final checklist item triggered Resume B generation live. The server log showed:

```
[Optimizer] attempt 1 rejected — section_growth: "Version Control Practice
  Project"; "Git"; "Cross-Browser Compatibility"; "Responsive Design Course"
```

The first generation attempt tried to add unproven claims corresponding to the just-confirmed checklist items; the guard rejected it and a second, honest attempt succeeded. This is the exact mechanism the project's own docs describe, caught actually operating on a real generation call — not previously proven live in this specific form.

**Downloads are real.** Both PDFs were fetched directly and inspected: `%PDF-` magic bytes, `application/pdf` content type, correct `Content-Disposition` filenames (`Audit-Tester-polished.pdf`, `Audit-Tester-target.pdf`), 4,462 and 4,586 bytes respectively.

**Live AI-gateway resilience, observed under real degraded conditions.** During this session's testing, the primary Gemini API key returned `403 Forbidden — Your project has been denied access`, and the OpenRouter key returned `402 — insufficient credits`. Every real scoring/generation call still completed successfully by falling through the provider chain (Gemini key 2 → OpenRouter key 2 → Cloudflare, depending on the call). This is the multi-key rotation built on 12 Aug, now seen carrying real production load through two simultaneously degraded providers. **Operational recommendation: the Gemini project access issue and the OpenRouter credit balance should both be addressed directly — the app is currently one more provider outage away from a real capacity problem, not a code problem.**

### 2.3 Real finding, not fixed: APP-12 — score inconsistency

The same underlying resume content scored:

|---|---|---|

| Resume A (reworded, same facts) | 68 | scored |

## 3. AI Search — state and path forward

### 3.1 What's confirmed working

The Opportunity Radar side (`frontend/lib/ai-search/agent-client.ts`, `app/api/ai-search/*`, `features/ai-search/components/ai-search-client.tsx`) is complete and defensively written:

- Agent-unreachable failures throw a distinct `AGENT_UNREACHABLE` error, surfaced honestly to the user rather than an infinite spinner.
- A 30-minute poll ceiling force-fails a genuinely stuck run rather than hanging forever.
- PDF magic bytes are checked before upload so a renamed `.docx` fails fast.
- One run per student at a time is enforced.

The agent repository itself (`/Users/laxmansirvi/ai  agent `) is well-architected: its stated invariants (never pad results, every `apply_url` resolves to a specific posting, a failed score is never a low score) are enforced in code, not just documentation.

### 3.2 What's new since 12 Aug

Real deployment tooling now exists: `deploy/oracle-setup.sh`, `deploy/install-services.sh`, `deploy/install-caddy.sh`, a `Caddyfile` implementing the shared-secret reverse-proxy gate the original handoff doc asked for, and four systemd units. **None of it has been executed.** No VM exists, no domain is pointed anywhere, and `curl` against `localhost:4300` returns connection refused.

A related frontend commit (`0f4d142`) added a shared-secret header (`X-Internal-Secret`) that the client now sends — but nothing on the agent side checks for it yet, and it isn't even set in any env file. The header is currently sent but unverified everywhere.

### 3.3 Corrected architectural detail

The original handoff doc characterized this as "six services, n8n, Postgres and Redis" running persistently. In fact, n8n runs as a one-shot CLI subprocess per job (`npx n8n execute --id ...`), not a persistent service — simpler ops than implied, though the stdout-scraping extraction (`extractResponse()` string-searches for `{"data"` in raw CLI output) is fragile by design.

This machine's local Postgres and Redis (via Homebrew, not Docker) are already running with the schema applied, and real provider API keys already populate the service `.env` files — this stack has clearly been run and tested locally before. The one missing piece for a **local** proof-run is `job-server/.env` (the only service directory without one).

### 3.4 Hard ceiling, independent of deployment

Per the agent's own `RUNBOOK.md`, a single resume run costs ~68,800 tokens across ~33 LLM calls. Groq's free tier is 100,000 tokens/day — **roughly one student per day, total**, once deployed, on free-tier quota. This is a commercial limit, not something a code change removes.

### 3.5 Path forward

See the migration prompt in the accompanying report (or ask for it directly) — the short version: prove the pipeline still runs locally first (cheapest, ~1 hour), then provision one VM and execute the deployment scripts that already exist (a few hours), then prove one real end-to-end run with every returned link HTTP-verified.

### 9.2 The Toaster bug — the highest-value finding of the day

While polishing the Search page's bookmark button, the natural next check — "does this show a confirmation?" — led to discovering that `<Toaster/>` (sonner's toast renderer) was mounted in exactly one place in the entire codebase: inside the Resume Builder's own `page-client.tsx`. Every other page calling `toast.success()/.error()/.loading()` — and a lot of pages do — had nothing anywhere in the render tree to display it.

**Live-confirmed, not inferred:** submitted a real ATS check on `/resume/ats`, which calls `toast.loading("Analyzing ATS Compatibility...")` on submit. The analysis itself completed correctly (a real score came back), but zero visual toast ever appeared anywhere on screen — confirmed by checking the DOM directly for sonner's signature `[aria-label="Notifications alt+T"]` container, which didn't exist on that page at all.

**Fixed:** the Toaster wrapper component (`packages/ui/src/components/sonner.tsx`) was missing its own `"use client"` directive — it only worked by accident while exclusively imported from an already-client-boundary file. Added the directive, mounted the Toaster once in the root `app/layout.tsx`, and removed the now-redundant local instance from the Resume Builder (two simultaneous Toasters would have double-rendered every toast there).

**Re-verified live:** resubmitted the identical ATS check — a real "✓ Analysis complete!" toast now renders bottom-right. Confirmed exactly one Toaster instance exists on the Resume Builder page post-fix (no duplicate-toast regression).

**Why this matters more than it might sound:** this silently affected loading states, success confirmations, and error messages across the ATS Checker, Resume Optimiser, AI Search, Tracker, notifications, and bookmarking — every one of those flows was working correctly underneath, but a user had no visual confirmation any of it happened. This is very likely why some earlier bug reports in this project's own history read as "nothing happens" — the backend worked, the feedback just never rendered.

### 9.3 Other real fixes

### 10.3 APP-13 — Hub crash on send

**Found, live, while sending a normal test message with an emoji:** the page crashed to the app's global error boundary ("Something went wrong!"). Console showed a `500` on `GET /api/hub/senders?ids=undefined` immediately followed by an uncaught `TypeError: Cannot read properties of undefined (reading 'replace')`.

**Root-caused:** a Supabase Realtime `postgres_changes` INSERT event for `hub_messages` came through with `payload.new` missing fields — confirmed directly via the guard's own diagnostic log after the fix, which caught the payload as a literal empty object `{}` on a deliberate rapid-fire repro (5 messages sent in quick succession reliably reproduced it twice). The cascade: `resolveSender(raw.sender_id)` was called with `sender_id === undefined`; `encodeURIComponent(undefined)` silently becomes the string `"undefined"` rather than throwing or producing an empty string; `/api/hub/senders` then queried `profiles WHERE id IN ('undefined')`, which Postgres rejects as an invalid UUID literal, 500ing; separately, the malformed message (now missing `created_at`) got added to `messages` state regardless, and `hub-client.tsx`'s `clearedAt` filter called `.replace()` on it directly with no guard — crashing the whole page.

**Fixed at every layer it touches, not just the one that crashed:**
1. `use-hub-messages.ts`: `resolveSender` returns the null-filled fallback immediately on a falsy id, without ever firing the request.
2. `use-hub-messages.ts`: the realtime INSERT handler now drops (logs and returns on) any payload missing `id`/`sender_id`/`created_at`, before it ever reaches `setMessages` — stops a malformed payload from becoming a message in state at all, which is where every downstream render assumption (timestamp formatting, sender name) lives.

### 10.4 APP-14 — bookmark check 406 spam

**Found:** `useBookmark`'s existence check (`features/opportunities/hooks/use-bookmark.ts`) used `.single()`, which 406s whenever a Supabase/PostgREST query returns zero rows — the *ordinary* outcome for "is this opportunity bookmarked yet" on any card the student hasn't saved. Confirmed live: loading `/search` (14+ opportunity cards) produced 14+ real `406` console errors, reproducible in a completely fresh tab with no prior navigation history.

**Fixed:** `.single()` → `.maybeSingle()`, which returns `{data: null, error: null}` on zero rows instead of erroring — the correct call for an existence check, and the same fix pattern Supabase's own docs recommend for exactly this. The feature was never actually broken (the bookmark icon's saved/unsaved state read correctly either way, since the code already checked `if (data)`), but every page load silently filled the console with errors that could mask a real one.

**Evidence:** re-tested `/search` and `/tracker` in fresh dev-server tabs post-fix — zero 406s. (Not yet re-verified against production at time of writing — ships in this pass's deploy alongside everything else in this section.)

### 10.5 APP-15 — Tracker hydration mismatch

**Found:** loading `/tracker` in a fresh tab threw a genuine, uncaught `Minified React error #418` (hydration mismatch) — reproduced independently of any other bug in this session, confirmed via console inspection in an isolated tab (not carried over from another page).

**Root-caused:** `daysBetween(from, to = new Date())` in `tracker-board.tsx` computed "now" via a bare default-parameter `new Date()`, evaluated separately by the server during SSR and by the client during hydration — two different wall-clock reads a moment apart. For a deadline sitting close to a day boundary relative to "now," the computed day-count (and therefore the badge text — "3d left" vs. "2d left") could differ between the two renders, which is exactly what React error #418 flags.

**Fixed:** `daysBetween`/`deadlineInfo` no longer default `to`/`now` internally — callers must pass it explicitly. Added `useClientNow()`, a small hook returning `null` until a `useEffect` (client-only, post-hydration) sets the real value — the same pattern already used in this codebase for `hub-message.tsx`'s timestamp formatting, for the identical reason. The `Card` component now renders no deadline/waiting badge on the very first paint (server and first client render both agree: nothing yet), then the real value fills in a frame after mount — imperceptible, and structurally impossible to mismatch since both renders now compute the identical "not yet available" state.

**Evidence:** re-tested `/tracker` in a fresh tab post-fix — zero hydration errors, deadline badges ("Listing closed", "Waiting 64d", etc.) render correctly with real data. Typecheck and lint clean (added the same `eslint-disable-next-line react-hooks/set-state-in-effect` — with the same justifying comment — this codebase already uses for the equivalent `hub-message.tsx` pattern).

### 10.6 APP-16 — dashboard "saved" count led to an empty page

**Found:** the dashboard's Progress Summary showed "SAVED: 10," linked to `/profile/saved` with copy calling it "opportunities waiting for action" — clicking through landed on a page reading "0 opportunities saved for later." Root-caused: `/profile/saved` filters out any bookmark whose opportunity has passed its deadline or is `Closed`/`Expired` before rendering (existing, correct behavior — a passed listing genuinely isn't "waiting for action"), but the dashboard's count was a raw `SELECT count(*) FROM bookmarks`, with no equivalent filter — so a fully-stale bookmark list (all 10 of this account's bookmarks, in this case) still produced a real, action-implying number pointing at an empty page. The same class of bug as this file's own APP-11 (a real number/claim with nothing behind it once you look).

**Fixed:** `app/(protected)/dashboard/page.tsx`'s saved-count query now fetches the joined opportunity `deadline`/`status` alongside each bookmark and applies the identical filter `/profile/saved` already uses, computed in JS rather than left to diverge as two independently-written filters.

**Evidence:** re-tested live post-fix — dashboard now correctly shows "SAVED: 0" for the same account, matching `/profile/saved` exactly; the "Review Saved Opportunities" recommended-action card (gated on `savedCount > 0`) correctly stopped appearing too, since it was equally misleading under the old count.
