# AI Agent Security Rules

## 1. Purpose

These rules are mandatory for all AI coding agents contributing to the Opportunity Radar project. AI agents must prioritize security over convenience and speed at all times. Any code generated by an AI must remain strictly consistent with the established `Security-Plan.md`. This ruleset exists to prevent the introduction of vulnerabilities, unauthorized data access, and insecure architectural patterns.

## 2. Authentication Rules

AI agents must:
* Use Supabase Auth as the sole authentication mechanism.
* Support Email/Password authentication.
* Support Google OAuth.
* Support GitHub OAuth.
* Use HttpOnly cookies for session storage via the `@supabase/ssr` package.
* Never use `localStorage` for authentication tokens.
* Never use `sessionStorage` for authentication tokens.

Explicitly prohibited:
* Custom authentication systems.
* Manual JWT creation, signing, or verification.
* Hardcoded credentials or secrets of any kind.

## 3. Authorization Rules

AI agents must:
* Verify roles (Student, Moderator, Admin) exclusively server-side.
* Never trust client-side role checks for authorization boundaries.
* Enforce the established Student, Moderator, and Admin RBAC model.
* Validate resource ownership strictly using `auth.uid()` against the relevant database records.

## 4. Database Rules

AI agents must:
* Enable Row Level Security (RLS) on every single table created.
* Create explicit, restrictive RLS policies for `SELECT`, `INSERT`, `UPDATE`, and `DELETE` operations.
* Follow the schema definitions in `Backend-Schema.md` exactly without introducing unauthorized tables or columns.
* Never expose the `SUPABASE_SERVICE_ROLE_KEY` to the client environment.
* Never bypass RLS unless specifically performing an isolated, authorized server-side action (e.g., audit logging).

## 5. API Rules

AI agents must:
* Validate all incoming API requests and server actions using Zod schemas.
* Return proper, standard HTTP status codes (e.g., 401, 403, 405, 500).
* Sanitize all user input to prevent injection attacks.
* Implement server-side authorization checks before executing any API logic.

Explicitly prohibited:
* Trusting any client-provided input without validation.
* Exposing stack traces, internal database schemas, or verbose errors in API responses.

## 6. Storage Rules

AI agents must:
* Enforce strict MIME-type validation for all uploads.
* Enforce file-size limits (maximum 2MB) for all uploads.
* Follow the specific bucket and RLS policies defined in `Security-Plan.md`.

## 7. Frontend Rules

AI agents must:
* Strictly avoid the use of `dangerouslySetInnerHTML`.
* Prevent Cross-Site Scripting (XSS) by relying on React's default auto-escaping.
* Protect secrets by never passing sensitive environment variables to Client Components.
* Use secure Next.js middleware routing to guard protected pages.

## 8. Environment Variable Rules

AI agents must:
* Never expose private keys, database passwords, or service role keys in client-side code.
* Only expose variables intentionally prefixed with `NEXT_PUBLIC_` to the browser.
* Never commit `.env.local` or any secrets to version control.

## 9. Dependency Rules

AI agents must:
* Prefer actively maintained, popular packages.
* Avoid abandoned packages or packages with known, unpatched vulnerabilities.
* Avoid introducing unnecessary dependencies that expand the project's attack surface.

## 10. Code Review Triggers

Mandatory human review is required for any AI-generated code that involves:
* Authentication changes
* Authorization changes
* Row Level Security (RLS) changes
* Infrastructure and environment variable changes
* Security policy changes

## 11. Forbidden Actions

AI agents are explicitly forbidden from performing the following actions:
* Disabling Row Level Security (RLS) on any database table.
* Storing auth tokens, session data, or sensitive PII in `localStorage` or `sessionStorage`.
* Exposing the `SUPABASE_SERVICE_ROLE_KEY` to the client side.
* Removing or bypassing server-side role checks.
* Skipping Zod validation on incoming API data.
* Disabling or bypassing rate limiting mechanisms.
* Committing secrets or hardcoding credentials in the codebase.

## 12. Compliance Checklist

Before any AI-generated code is considered acceptable, the agent must verify:
- [ ] No `localStorage` or `sessionStorage` is used for auth.
- [ ] `HttpOnly` cookies handle all session management.
- [ ] Zod validates all API input.
- [ ] Server-side logic explicitly checks authorization roles.
- [ ] RLS is enabled and policies are explicitly defined.
- [ ] No secrets are exposed to the client or hardcoded.
- [ ] `dangerouslySetInnerHTML` is not utilized.

## 13. Security Headers Rules

AI agents must:
* Preserve CSP
* Preserve HSTS
* Preserve X-Frame-Options
* Preserve Referrer-Policy
* Preserve Permissions-Policy

AI agents must never weaken or remove security headers.

## 14. CORS Rules

AI agents must:
* Allow only approved origins
* Never use wildcard (*) origins
* Never allow credentials from unapproved origins

## 15. Logging Rules

AI agents must:
* Preserve audit_logs integrity
* Log moderator actions
* Log admin actions

AI agents must never log:
* Passwords
* Tokens
* Secrets
* Sensitive credentials

## 16. Documentation Compliance Rules

AI agents must strictly follow:
* PRD.md
* TRD.md
* App-Flow.md
* UI-UX-Brief.md
* UI-SCREEN-MAP.md
* Backend-Schema.md
* Implementation-Plan.md
* Security-Plan.md

AI agents must not introduce undocumented features or architecture changes.
